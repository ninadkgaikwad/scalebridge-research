\section{Purpose and Authority}
This document records the current executable Day-1 production architecture for the PINODE/EPSR paper after Patch01R2B qualification. It is intended to answer, in one place, the following questions:
\begin{itemize}[nosep]
  \item What constitutes a scientific model configuration and how are the 32 configurations formed?
  \item What campaign scopes exist and how many configurations does each run?
  \item Which HPO parameters exist for each method and RC order, and what are their exact Optuna search spaces?
  \item Which values are campaign/HPO protocol settings rather than method hyperparameters?
  \item Where is each item defined in code, and which source is actually authoritative at runtime?
  \item How are HPO data selected, split, persisted, resumed, frozen, and handed to final training?
  \item How are multi-start training, checkpoint acceptance, restart selection, Sim1/Sim2/Sim3, Phase-C HVAC power, and controller overrides organized?
\end{itemize}

\subsection{Current qualified baseline}
The implementation documented here corresponds to the installed Patch01R2B production infrastructure. The targeted real-data validator passed 135/135 tests, and the Micro32 campaign completed and accepted all 32 configurations with zero rejected and zero failed configurations. Micro32 is a plumbing qualification and is not a model-performance result.

\subsection{Important current authority rule}
The method-specific HPO ranges are \textbf{not campaign-definition fields}. The campaign says which scientific configurations to run and supplies the HPO/training protocol budget. The method trainer owns the scientific search space. In addition, the current CLI constructs \code{HPOConfig} and \code{ProductionTrainingConfig} directly from command-line arguments/defaults. Editing only the \code{hpo:}, \code{training:}, or \code{evaluation:} sections of \path{configs/production.yaml} does not currently change a \code{campaign} run. The \code{controller:} section is different: it is actively read by default.

\subsection{Production campaign}
For each selected scientific configuration, production follows:
\[
\boxed{\text{HPO once}}\rightarrow
\boxed{\text{freeze HP}}\rightarrow
\boxed{\text{full TRAIN multi-start}}\rightarrow
\boxed{\text{acceptance gates}}\rightarrow
\boxed{\text{VALIDATION chooses restart}}\rightarrow
\boxed{\text{final TEST Sim1/2/3}}.
\]

\begin{enumerate}
  \item Load the real Phase-D case and Phase-C models.
  \item Calibrate aggregate/Dining/Kitchen thermostat behavior from exact 300-s TRAIN transitions, subject to explicit user overrides.
  \item Run persistent TRAIN-only HPO once for the scientific configuration.
  \item Freeze the best HPO values.
  \item For each requested restart seed, rebuild the model with frozen HPs and train on full authoritative TRAIN.
  \item Use Phase-D VALIDATION for early stopping/best validation score and for choosing among accepted restarts.
  \item Save a candidate checkpoint and apply integrity/functionality acceptance gates. Short TEST smokes are gates only; they do not choose the restart.
  \item Select the accepted restart with lowest validation score (seed breaks ties deterministically).
  \item Run final Sim1, Sim2, and Sim3 on TEST only; production Sim2 and Sim3 process all contiguous monthly TEST episodes.
\end{enumerate}

\section{HPO Data Contract}
\subsection{Partition ownership}
HPO uses Phase-D TRAIN only. Phase-D VALIDATION and TEST never enter HPO. After HPO is frozen, full TRAIN is used for production fitting, VALIDATION is used for early stopping/restart selection, and TEST is reserved for final Sim1/2/3 and short checkpoint functionality gates.

\subsection{Month-balanced floor arithmetic}
For month $m$ with $N_m$ authoritative TRAIN rows and requested HPO percentage $p$,
\[
N_{\mathrm{HPO},m}=\left\lfloor N_m\frac{p}{100}\right\rfloor.
\]
For requested inner holdout fraction $h$,
\[
N_{\mathrm{hold},m}=\left\lfloor N_{\mathrm{HPO},m}\frac{h}{100}\right\rfloor,
\qquad
N_{\mathrm{fit},m}=N_{\mathrm{HPO},m}-N_{\mathrm{hold},m}.
\]
The sampler never rounds upward, oversamples, or silently changes the requested HPO/holdout percentages. Encoder-history rows may be read as causal context from the same TRAIN segment, but context rows are not HPO optimization/holdout target rows and do not inflate the percentage.

\subsection{Geometry feasibility}
The sampler guarantees at least one legal fit and holdout rollout for the HPO protocol's declared conservative geometry. If the floored budget cannot support the selected $N_r/L_e$ geometry, the request fails explicitly and reports that the user should either increase the HPO percentage or reduce the allowed geometry. Micro32 intentionally uses $N_r\le3$ so 0.5\% remains feasible. Production retains $N_r\le12$ and $L_e\le12$.

\section{Optuna Study, Persistence, and Resume Contract}
Production uses \code{optuna.samplers.TPESampler}. The study is stored in SQLite at a configuration/protocol-specific path and is created with \code{load_if_exists=True}.

\subsection{Scientific protocol identity}
Study identity contains the scientific configuration plus the HPO protocol, including the sampling protocol version. The current implementation removes only \code{n_trials} and \code{timeout_seconds} from the identity payload. Therefore:
\begin{itemize}
  \item Increasing only \code{n_trials} resumes the same compatible study and runs only enough additional trials to reach the requested total completed-trial target.
  \item Changing TRAIN percentage, holdout, objective, per-trial epoch/patience budget, HPO seed, batch/window policy, sampling blocks, rollout/history geometry, or the scientific configuration creates a distinct protocol ID/study.
  \item Trial count is an execution budget, not a scientific protocol field.
\end{itemize}

\subsection{Effective batch-size caveat}
The method-owned NODE/PINODE search space includes \code{batch_size=64}, but \code{run_persistent_hpo} executes each trial with
\[
\text{effective HPO batch size}=\min(\text{sampled batch size},\;\texttt{HPOConfig.max\_batch\_windows}).
\]
The default HPO cap is 32. Consequently, a trial whose recorded Optuna parameter is 64 is actually evaluated with an effective HPO batch size of 32. Frozen hyperparameters still record 64, and final production training uses
\[
\min(\text{frozen batch size},\;\texttt{ProductionTrainingConfig.max\_batch\_windows}),
\]
whose default cap is 64. Therefore the current implementation can evaluate a recorded HPO choice of 64 using effective 32 and then use 64 in final training. This is a current implementation detail that should be reviewed before interpreting batch-size HPO scientifically.

\section{Sim3 Thermostat and Controller Overrides}
The default thermostat deadband is derived from exact 300-s adjacent TRAIN pairs. Explicit override values are half-widths about the active setpoint:
\[
T_{\mathrm{lower}}=T_{\mathrm{set}}-\Delta T_{db},\qquad
T_{\mathrm{upper}}=T_{\mathrm{set}}+\Delta T_{db}.
\]
Thus \code{deadband_half_width_C: 1.0} means $\pm1^\circ$C and a 2 $^\circ$C total hysteresis band.

\begin{table}[h]
\centering
\begin{tabularx}{\textwidth}{L{0.34\textwidth}Y}
\toprule
\textbf{Override field} & \textbf{Meaning} \\
\midrule
Global \code{deadband_half_width_C} & Applies to all controlled zones unless a zone-local override exists. \\
Global \code{heating_mode_deadband_half_width_C} & Same precedence for heating-mode switching deadband. \\
Zone-local deadband fields & Override global deadband for that physical controller. \\
\code{cooling/heating.T_supply_C} & User supply-temperature override. \\
\code{cooling/heating.mdot_nominal_kg_s} & User nominal mass-flow override. \\
\code{cooling/heating.mdot_max_kg_s} & User maximum mass-flow override; must be $\ge$ nominal. \\
\bottomrule
\end{tabularx}

Resolution precedence is
\[
\boxed{\text{user override}} > \boxed{\text{observed TRAIN data}} > \boxed{\text{documented fallback}}.
\]
Kitchen heating remains explicitly extrapolative/OOD if heating was unobserved in TRAIN, even when a user provides heating actuation values. Backward-compatible provenance strings are preserved while richer source-class fields are recorded separately.

\section{Phase-C HVAC Chain in Sim3}
The offline controller/power chain is
\[
\dot m,T_s,T_z
\rightarrow Q_{\mathrm{HVAC,physics}}
\rightarrow Q_{\mathrm{HVAC,PhaseC}}
\rightarrow |Q_{\mathrm{HVAC,PhaseC}}|
\rightarrow P_{\mathrm{HVAC,model\ raw}}
\rightarrow P_{\mathrm{HVAC,physical}}\ge0,
\]
with
\[
Q_{\mathrm{HVAC,physics}}=1000(1.005)\dot m(T_s-T_z).
\]
The Phase-C model ID historically named \code{QAC} maps physics HVAC heat to corrected/effective HVAC heat. The PHVAC model consumes the absolute corrected HVAC heat. Both raw regression PHVAC and nonnegative physical PHVAC are retained in outputs/provenance.

\section{Implementation Notes to Preserve}
\begin{enumerate}
  \item Campaign matrix science, method search-space science, and execution budgets are intentionally separated.
  \item TRAIN percentage and inner holdout are strict non-exceeding floor budgets per month.
  \item HPO context never converts context rows into target rows and never crosses authoritative TRAIN boundaries.
  \item Changing only target trial count resumes a compatible study; changing scientific HPO protocol creates a different study.
  \item Seeds are training restarts, not new scientific model configurations.
  \item VALIDATION selects among accepted restarts; TEST is not a model-selection partition.
  \item Sim2/Sim3 production evaluation resets at monthly TEST episode boundaries.
  \item Default controller behavior remains data-derived; user overrides are explicit and provenance-recorded.
  \item The current \path{production.yaml} HPO/training/evaluation blocks are not authoritative for the \code{campaign} CLI; CLI arguments/dataclass defaults are. Do not assume editing YAML alone changes those campaign settings.
  \item Before interpreting batch size as a scientifically tuned HPO parameter, review the current HPO effective cap of 32 versus the method search choice of 64 and final-training cap of 64.
\end{enumerate}
