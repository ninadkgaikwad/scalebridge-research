\section{Purpose and governing separation}
The production configuration system is intentionally divided into two layers:

\begin{verbatim}
production.yaml
    = experiment policy, budgets, evaluation policy, controller policy

training/trainer.py
    = method-owned scientific HPO search spaces
\end{verbatim}

The campaign YAML answers \emph{what to run, how much compute/data to allocate, how to evaluate it, and what controller policy to use}. It does not redefine which hyperparameters are scientifically meaningful for each method. Those search spaces remain method-owned in \path{Paper_PINODE_EPSR/src/pinode_epsr/training/trainer.py}.

\section{Control-surface hierarchy}
After Patch01R3, the authoritative control hierarchy is:

\begin{verbatim}
production.yaml
|
+-- campaign     -> WHAT scientific configurations/restarts run
+-- hpo          -> HOW hyperparameters are selected
+-- training     -> HOW the final frozen model is trained
+-- evaluation   -> HOW Sim1/Sim2/Sim3 are executed
+-- controller   -> HOW thermostat/HVAC actuation behaves in Sim3

NOT IN YAML
+-- method search spaces -> WHAT each method is allowed to tune
                           (training/trainer.py)
\end{verbatim}

\paragraph{Required R3 consumption path.}
\begin{verbatim}
production.yaml evaluation block
    -> strict typed ProductionEvaluationConfig
    -> resolved CLI/YAML configuration
    -> campaign.py
    -> run_offline_evaluations(evaluation_config=...)
    -> sim1 / sim2 / sim3
       -> sim3 receives cooling_mdot_choice,
                        heating_mdot_choice,
                        unobserved_mode_policy
\end{verbatim}

Invalid strings such as \code{cooling_mdot_choice: average} or \code{unobserved_mode_policy: maybe} must fail configuration validation rather than silently defaulting.

\subsection{Unobserved-mode semantics}
With \code{fallback}, an unobserved requested mode remains executable through the resolved profile:
\begin{verbatim}
unobserved requested mode
    -> explicit user override if supplied
       otherwise documented same-zone opposite-mode fallback
    -> apply nominal/max selector
    -> execute Sim3
    -> preserve observed_in_train=false and extrapolation/OOD provenance
\end{verbatim}

With \code{error}, the simulation fails only if that unobserved mode is actually requested; merely having an unobserved mode in calibration does not cause preemptive failure.

\subsection{Resolution precedence and null semantics}
For controller actuation values:
\begin{verbatim}
explicit user override
    > observed TRAIN-derived mode value
    > documented same-zone opposite-mode fallback
\end{verbatim}

Null never means zero. It means ``do not replace the qualified resolved value.'' For Kitchen heating, which is unobserved in TRAIN, a user override can replace fallback physical values but must never remove the facts that the mode was unobserved and its use is extrapolative/OOD.

\subsection{Kitchen heating example}
If YAML specifies

      heating:
        T_supply_C: 34.0
        mdot_nominal_kg_s: 0.8

then an actual Kitchen heating request uses $T_{sa}=34$ C and $\dot m=1.1$ kg/s, while provenance continues to record that Kitchen heating was not observed in TRAIN and is extrapolative.

\section{CLI override contract}
After R3, argparse defaults for YAML-owned fields must be \code{None} (or equivalent tri-state semantics) so omission means inheritance rather than a hidden CLI default.

\begin{verbatim}
python ... run_day1_production.py campaign
    -> use production.yaml exactly

python ... campaign --hpo-trials 50
    -> use production.yaml except hpo.n_trials = 50 for this run
\end{verbatim}

Boolean fail-fast semantics require three states: inherit YAML, explicitly fail-fast, or explicitly continue-on-error. The CLI should preserve \code{--fail-fast} and provide a symmetric explicit false control such as \code{--continue-on-error}.

Evaluation overrides shall likewise be explicit, for example:
\begin{verbatim}
--cooling-mdot-choice nominal|max
--heating-mdot-choice nominal|max
--unobserved-mode-policy fallback|error
\end{verbatim}
and omitted values inherit YAML.

\section{Resolved configuration and provenance}
Every production campaign must persist both the source configuration and the fully resolved runtime configuration. At minimum:

\begin{Verbatim}[fontsize=\small]
production_config:
  source_path: .../configs/production.yaml
  source_sha256: <sha256>

resolved_configuration:
  campaign: ...
  hpo: ...
  training: ...
  evaluation: ...
  controller: ...

field_provenance:
  hpo.n_trials:
    value: 24
    source: cli_override
    yaml_value: 12
    cli_value: 24
    category: COMPUTE_BUDGET

  evaluation.heating_mdot_choice:
    value: nominal
    source: production_yaml
    category: CONTROLLER_POLICY
\end{Verbatim}

The accepted provenance sources include at least \code{production_yaml}, \code{cli_override}, and \code{micro32_qualification_override} where applicable.

\section{Machine-independent scientific identity}
Absolute filesystem paths are audit provenance, not scientific identity. If two machines resolve byte-equivalent scientific configuration values from equivalent YAML content, their production scientific identity must not differ merely because one source path is on \code{C:\textbackslash} and another on \code{D:\textbackslash} or a Linux path. Source path and SHA-256 remain in manifests, but canonical scientific IDs are based on resolved scientific values rather than absolute config paths.

\section{Micro32 separation}
Micro32 is an explicitly separate qualification profile. It already qualified 32/32 configurations under the R2B science contract. Patch01R3 must not make edits to production YAML silently change the micro qualification geometry.

The intended distinction is:
\begin{verbatim}
production campaign
  -> base values from production.yaml

micro32 qualification
  -> explicit micro qualification overrides
     HPO percentage ~0.5%
     1 trial
     1 HPO epoch
     N_r <= 3
     bounded evaluation
  -> controller values may still resolve from common controller config
  -> manifest source = micro32_qualification_override for micro-specific fields
\end{verbatim}

\section{Causal examples}
\subsection{Changing only HPO trial count}
If only
\begin{Verbatim}[fontsize=\small]
hpo:
  n_trials: 30
\end{Verbatim}
changes, then the causal path is
\begin{verbatim}
YAML -> resolved HPOConfig -> more Optuna candidate evaluations
     -> best candidate may change -> final training may change
     -> resulting Sim1/2/3 outputs may change
\end{verbatim}
while model equations and search-space definitions remain unchanged.

\subsection{Changing only heating mdot policy}
If only
\begin{Verbatim}[fontsize=\small]
evaluation:
  heating_mdot_choice: max
\end{Verbatim}
changes, then HPO, final training, checkpoint, Sim1, and Sim2 are unchanged. Sim3 uses maximum resolved heating airflow instead of nominal airflow whenever heating is requested.

\subsection{Changing only ordinary deadband}
If only
\begin{Verbatim}[fontsize=\small]
controller:
  deadband_half_width_C: 1.0
\end{Verbatim}
changes, then HPO/training/Sim1/Sim2 remain unchanged, while Sim3 ordinary HVAC switching thresholds become setpoint$\pm1$ C (2 C total band), potentially changing HVAC timing, $Q_{HVAC}$, PHVAC, and recursive temperature trajectory.

\section{Strict validation requirements}
Patch01R3 configuration resolution must reject:
\begin{itemize}[nosep]
\item unknown top-level sections;
\item unknown keys within known sections;
\item invalid enum values;
\item out-of-range percentages, negative budgets, or invalid nonpositive integer budgets;
\item negative mdot values;
\item mode profiles where explicit max mdot is less than explicit nominal mdot;
\item invalid controller zone names;
\item invalid booleans/types that would otherwise be silently coerced in a scientifically ambiguous manner.
\end{itemize}

A typo such as \code{hpo.n_trial} must fail rather than being silently ignored.

\section{Required R3 validation coverage}
Before Patch01R3 is accepted, tests must establish at least:
\begin{enumerate}[nosep]
\item strict YAML schema and typed construction;
\item omitted CLI fields inherit YAML;
\item explicit CLI values override exactly one intended field and record provenance;
\item machine path does not contaminate scientific configuration identity;
\item HPO protocol-ID behavior remains compatible with R2B policy;
\item evaluation budget fields are consumed by Sim1/Sim2/Sim3;
\item nominal versus max cooling/heating mdot choices change the actual Sim3 command source appropriately;
\item cooling and heating selectors are independent;
\item \code{unobserved_mode_policy=fallback} executes resolved fallback/override and preserves OOD tags;
\item \code{unobserved_mode_policy=error} fails only upon actual use of an unobserved mode;
\item invalid evaluation values fail before simulation;
\item controller null semantics preserve qualified data-derived behavior;
\item Patch2/3/4/5/R2B regressions and bounded real Phase-B/C/D validation remain green.
\end{enumerate}

\section{Final design rule}
The complete design is summarized by three sentences:

\begin{enumerate}
\item \textbf{The YAML says what experiment to execute and with what budgets/policies.}
\item \textbf{The method code says which hyperparameters are scientifically searchable and what the model means.}
\item \textbf{The resolved manifest says exactly what was actually executed, where every value came from, and how it affected runtime.}
\end{enumerate}

This separation is the accepted Patch01R3 design contract and shall be treated as frozen input to subsequent implementation.
