==========================================

Context
-------
This document summarizes the current validated MLflow configuration used by
ScaleBridge for the Building-Grid Intelligence Research Studio Settings -> MLflow
page.

The Settings -> MLflow page should be an inspect-and-validate configuration page.
It should not silently start or stop MLflow servers unless a future managed
server-control policy is explicitly implemented.

2. TRACKING URI SELECTION LOGIC
===============================

Field: MLflow Tracking URI
--------------------------
Label:
    MLflow Tracking URI

Value / behavior:
    MLFLOW_TRACKING_URI, usually http://127.0.0.1:5000

Source of truth:
    Environment variable setup in README/context.

Validation rule:
    URI is nonempty and reachable by MLflow client or HTTP health check.

Pass meaning:
    Server responds and experiments can be listed.

Warning meaning:
    Environment variable is missing, but default localhost is assumed.

Failure meaning:
    Client cannot connect.

Help-popup explanation:
    This is the MLflow tracking endpoint used by ScaleBridge scripts. For local
    Windows runs, use http://127.0.0.1:5000.


Field: Tracking URI fallback
----------------------------
Label:
    Tracking URI fallback

Value / behavior:
    Export script defaults to MLFLOW_TRACKING_URI or localhost if not provided.

Source of truth:
    scripts/mlflow/export_mlflow_runs.py argument behavior.

Validation rule:
    If user leaves the field blank, the app should show the inferred value.

Pass meaning:
    Inferred URI resolves.

Warning meaning:
    Inferred URI is shown but not validated.

Failure meaning:
    No URI and no localhost server.

Help-popup explanation:
    Leave blank to use the environment/default local MLflow server, or override
    for inspection.

16. SHOULD DASH INSPECT MLFLOW OR START THE SERVER?
===================================================

Current Settings -> MLflow implementation policy:

    Dash should inspect and validate MLflow configuration.
    Dash should display/copy the validated server startup command.
    Dash should not automatically start or stop the MLflow server by default.

Reason:
    The validated workflow starts MLflow with a terminal command, and no server
    shutdown behavior is defined in the current handoff. The Settings page can
    safely check whether the UI is reachable, show the active tracking URI,
    inspect export/registry files, and show pass/warning/failure states.

Future possibility:
    Starting a long-lived server from Dash should only be added as an explicit
    future action after process ownership, logging, shutdown, and port-conflict
    behavior are defined.

18. SETTINGS-PAGE SUMMARY
=========================

The Settings -> MLflow page should answer four questions:

    1. What MLflow server/config am I pointing to?
    2. Is it reachable and consistent with the selected machine?
    3. What experiments/runs have been exported and merged?
    4. Where should Dash look for artifacts and registry summaries?

It should not silently start or stop servers yet. It should present validated
commands, validation checks, and clear pass/warning/failure statuses.
